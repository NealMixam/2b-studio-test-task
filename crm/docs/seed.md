# Тестовые данные

Предпочтительный способ — создать трёх пользователей через Supabase Auth Admin API или панель Users и добавить профили по инструкции README. Для полностью пустого отдельного тестового проекта есть вспомогательный генератор:

```sh
node crm/scripts/create-demo-sql.mjs
```

Он создаёт в игнорируемой папке `.tmp` файлы `setup-demo.sql`, `demo-access.json` и `Доступы для проверки.md`. Пароли случайные, не выводятся в консоль. SQL нужно выполнить один раз после основной миграции. Скрипт создаёт Auth users и identities непосредственно в SQL; это вспомогательный установщик для демонстрации, зависящий от схемы Supabase Auth, а не штатный механизм управления сотрудниками. При повторном запуске он не перезаписывает доступы. Действующие аккаунты не изменяются.

Данные: постановщик Алексей Смирнов, исполнители Иван Петров и Мария Волкова; 3 объекта и 6 задач, все пять статусов. История создаётся теми же функциями базы, что использует приложение. Наполнение выполняется в транзакции.

Проверка установленного облачного проекта:

```sh
node --env-file=crm/.env.local crm/scripts/verify-cloud.mjs
```

Скрипт входит под тремя тестовыми учётными записями из `.tmp/demo-access.json`, проверяет RLS и ограничения через HTTP API, создаёт отдельный временный объект, проходит цикл задачи и удаляет только этот временный объект в `finally`. Рабочие демонстрационные задачи не меняет. Не запускайте скрипт с производственными учётными записями.

Не публикуйте `.tmp`, пароли и SQL с паролями. Передавайте файл доступов проверяющему отдельно.
