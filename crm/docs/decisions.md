# Решения и допущения

1. Все постановщики равноправны и видят все объекты и задачи, в том числе созданные другим постановщиком. Это одна компания, без разделения на организации.
2. Назначать можно только пользователя с ролью исполнителя. Постановщик не совмещает обе роли в одной учётной записи.
3. При создании задачи фиксируется запись «Задача создана» с пустым предыдущим статусом. Каждая последующая смена статуса создаёт новую запись.
4. Постановщик редактирует название, описание, объект и исполнителя в любом статусе, но не автора, дату или статус напрямую. Переназначение сохраняет текущий этап; новый исполнитель получает доступ, предыдущий теряет его.
5. Принятая задача завершена: повторное открытие не предусмотрено указанной в ТЗ схемой.
6. Комментарий необязателен при остальных переходах; для доработки обязателен, пробелы не считаются текстом. Ограничение — 2000 символов.
7. Удаление объекта каскадно удаляет его задачи и историю. Удаление задачи удаляет её историю. Это доступно только постановщику с явным подтверждением в интерфейсе. История не является юридическим архивом; неизменяемость действует пока существует задача. Если нужен вечный архив, следует заменить физическое удаление архивированием.
8. Исполнитель видит имя автора/участника истории своей задачи, но не каталог всех сотрудников и не чужие задачи. Email сотрудников в таблице профилей не хранится.
9. Новые пользователи и роли создаются администратором Supabase. Открытой регистрации и экрана управления сотрудниками нет.
10. Время хранится в UTC, отображается в часовом поясе браузера. Порядок истории определяется монотонным ID.
11. Данные обновляются после действий и кнопкой обновления. Realtime, вложения, уведомления, сроки и поиск по описанию не входят в ТЗ.
12. Для малого объёма CRM доступные записи загружаются страницами по 500, фильтрация выполняется в браузере. При росте объёма нужны серверные фильтры и постраничные экраны.
13. Защита проверяется в PostgreSQL, интерфейс лишь повторяет ограничения для удобства. Администратор базы и service_role относятся к доверенной инфраструктуре; их возможности шире клиентского API.
14. Повторная смена статуса с устаревшего экрана отклоняется базой. Редактирование реквизитов использует принцип последней записи; версионирование реквизитов не запрошено.

Возможности сверх задания: поиск, фильтр статусов, адаптивная вёрстка, состояние загрузки, сообщения об ошибках, подтверждение удаления и автоматические проверки безопасности.
