# Контур — объекты и задачи

Мини-CRM строительной компании: React 19 + TypeScript + Vite + Supabase Auth/PostgreSQL. Интерфейс на русском, адаптивная вёрстка, две роли, управление объектами и задачами, история статусов.

## Быстрый запуск

Node.js 22.12+ (проверено на 24).

```sh
npm --prefix crm ci
cp crm/.env.example crm/.env.local
# Заполните VITE_SUPABASE_URL и VITE_SUPABASE_PUBLISHABLE_KEY
npm run dev
```

PowerShell: вместо `cp` можно `Copy-Item crm/.env.example crm/.env.local`. На Windows с ограничением запуска скриптов используйте `npm.cmd`.

```sh
npm test       # тесты реальной SQL-миграции в PostgreSQL WASM (PGlite)
npm run build # TypeScript + production-сборка, результат dist/
```

## Настройка Supabase

1. Создайте отдельный проект. В SQL Editor выполните `crm/supabase/migrations/202611110001_crm.sql`. Миграция применяется один раз, целиком, в транзакции. Через CLI: из папки `crm` выполните `supabase link --project-ref YOUR_REF`, затем `supabase db push`.
2. Authentication → General configuration: отключите **Allow new users to sign up**. Это настройка сервиса Auth, SQL-миграция её не меняет. Для локального Supabase она задана в `crm/supabase/config.toml`.
3. Создайте пользователей через Authentication → Users → Add user, с подтверждённым email. Минимум один постановщик и два исполнителя. Не используйте реальные рабочие пароли.
4. Добавьте профили из SQL Editor, подставив UUID созданных пользователей:

```sql
insert into public.profiles(id, full_name, role) values
('UUID_1', 'Алексей Смирнов', 'manager'),
('UUID_2', 'Иван Петров', 'worker'),
('UUID_3', 'Мария Волкова', 'worker');
```

5. Войдите постановщиком, создайте объекты и задачи. Скрипт `crm/scripts/seed.mjs` автоматизирует наполнение через обычные пользовательские сессии: пример настроек в `crm/docs/seed.md`.
6. Для публикации разместите `dist/` на статическом хостинге. Маршруты используют hash, серверные перенаправления не нужны. Укажите адрес сайта в Supabase Auth Site URL. Параметры `VITE_*` подставляются во время сборки; после их изменения нужна новая сборка.

## Безопасность

- Чтение защищено RLS на всех четырёх таблицах. Исполнитель видит только свои задачи, их объекты и историю; постановщик — все.
- Прямые INSERT, UPDATE, DELETE не разрешены ни одной клиентской роли. Запись выполняется через ограниченные RPC, которые сами проверяют права.
- Роль берётся из `profiles`, а не из пользовательских метаданных. Клиент не может изменить роль или создать профиль.
- Переходы дополнительно проверяет триггер базы. RPC блокирует строку и сверяет ожидаемый статус, защищая от повторных и устаревших запросов.
- Историю пишет только триггер в той же транзакции. Клиент не задаёт автора, дату или старый статус и не может отдельно менять историю.
- Все SECURITY DEFINER функции используют пустой `search_path`, полные имена таблиц и явные разрешения EXECUTE. Служебные функции недоступны клиенту.
- В браузер передаётся только публичный publishable/anon key. `service_role`, PAT, пароли тестовых пользователей и локальные `.env*` исключены из Git.
- Исключение для истории: при разрешённом удалении задачи/объекта постановщиком история удаляется каскадно. Отдельное удаление истории запрещено.

Решения сверены с [документацией RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [функциями базы](https://supabase.com/docs/guides/database/functions) и [настройками регистрации](https://supabase.com/docs/guides/auth/general-configuration).

## Проверки

`npm test` поднимает изолированную PostgreSQL-базу PGlite, создаёт эквивалент `auth.uid()` и применяет исходную миграцию без замены бизнес-логики. Проверяются обе роли, 50 комбинаций переходов, прямые попытки обойти API, история, комментарии, переназначение, CRUD и каскадное удаление. Эти тесты не заменяют проверку сервиса Supabase Auth и HTTP API в облаке.
